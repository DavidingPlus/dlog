# 分段缓冲与日志提交优化方向

状态：方案讨论阶段，尚未实现或验证。本文记录后续优化方向，现有行为以当前代码为准；性能收益和具体接口均待实现与测试确认。

## 1. 背景与目标

目前一条日志先由 `LogMessage` 内的 `LogStream` 格式化到独立的 `FlexibleBuffer`。消息完成后，`LogMessage` 通过回调将 `const LogStream &` 交给 `Logger`，再由 `LogWorker::append()` 把其中的字节复制到生产者缓冲区。后台任务交换生产者与消费者缓冲区，在锁外输出并刷新。

这条路径保证了消息析构后后台仍能安全使用数据，但也产生了从消息缓冲区到 Worker 缓冲区的一次额外字节复制。生产者在持锁期间完成这次复制；生产者缓冲区扩容时还可能移动已有数据。

本方案的主要目标是：**将已格式化日志所在缓冲区的所有权从 `LogMessage` 转交给 `LogWorker`，使消息提交到生产者缓冲区时不复制日志字节。**

这里的“零拷贝”只指上述交接边界。它不代表格式化、消息缓冲区扩容、标准 I/O 缓冲或操作系统写入过程没有其他复制，也不承诺端到端零拷贝。

## 2. 拟议设计

将 `LogWorker` 的 `m_producerBuffer` 和 `m_consumerBuffer` 改为分段缓冲区。每段拥有一个已格式化的 `FlexibleBuffer`；`SegmentedBuffer` 按提交顺序持有这些段，直到后台输出完成。

```text
生产者线程
  LogMessage → LogStream → FlexibleBuffer（完整的一条日志）
                                  │
                                  │ 交接所有权，不复制日志字节
                                  ▼
  m_producerBuffer: [日志 1 的段] [日志 2 的段] ...
                                  │
                                  │ 持锁交换生产者与消费者缓冲区
                                  ▼
  m_consumerBuffer: [日志 1 的段] [日志 2 的段] ...
                                  │
                                  │ 后台在线程锁外逐段 write，整批 flush 一次
                                  ▼
                                输出目标
```

上图中“线程锁外”指不持有 Worker 的生产者状态锁；输出目标可以有自己的同步机制。初步以一条消息对应一个段为模型，不把多个消息合并为连续内存。后台完成一批后清空消费者缓冲区并释放段，是否复用段及如何限制保留内存留待性能数据支持后决定。

`SegmentedBuffer` 首先只需满足 Worker 的实际需求：接收拥有所有权的段、判空、按顺序访问各段，以及输出后清空。容器类型、是否维护字节总数和接口细节留待实现时确定，不预设共享内存、切片、随机访问或通用网络 I/O 能力。

### 2.1 所有权和接口

1. 日志格式化仍由每条 `LogMessage` 独立完成，包括提交前追加结尾内容。
2. 完成后回调必须能够交出底层缓冲区；当前 `OutputFunc` 接收 `const LogStream &`，只允许借用，不能直接完成所有权转移。应明确回调何时消费数据，并同步更新调用方与测试。
3. Worker 检查后台错误后，在现有互斥锁保护下接收完整段并安排任务。接收成功后，后台输出期间数据由 Worker 持有，不依赖 `LogMessage` 或其 `LogStream` 的生命周期。
4. 移交方式可以是移动 `FlexibleBuffer` 的值，或转移拥有整个缓冲区的指针。两者需结合现有对象布局、分配次数、接口兼容性和异常安全确定，不能仅凭 `std::move` 就认定没有复制。

当前 `FlexibleBuffer` 使用 `std::vector<char>` 及读写索引，并显式声明了析构函数，因而不会隐式生成移动构造函数。若选择移动值，须显式设计移动操作：目标保留正确的可读范围，被移动对象满足清晰、可安全析构和按约定使用的不变量；不能只移动 vector 而把原对象索引留在无效状态。验证实际转移底层存储，不复制字节。

目前公开的 `LogWorker::append(const char *, size_t)` 只有借用的指针与长度，无法推断数据的所有权或生命周期；为保持其现有调用语义，需要继续复制，除非另行定义明确的所有权转移接口。现有 `append(const LogStream &)` 和 `LogMessage::OutputFunc` 的直接调用者、公开头文件及外部用户也需要检查；具体保留兼容重载还是迁移接口，实施时依据实际使用情况确定。

### 2.2 顺序、并发与关闭

- 一条完整消息作为一个单位入队，在同一 Worker 中按成功接收顺序输出，不让不同生产者的消息字节交错；不承诺不同 Worker 的全局顺序。
- 保留现有双缓冲交接与按需调度：非空数据到来后安排后台任务；同一 Worker 同时最多一个任务排队或执行；检查待写数据和任务状态使用同一把锁，避免遗漏调度。
- 后台输出和刷新不持有生产者状态锁；输出期间生产者可以继续追加到另一组缓冲区。
- 正常停止、析构等待、启动前或停止后追加及重启等行为沿用当前 Worker 约定。调用方仍需按现有要求在停止前结束生产者和临时消息。
- 段的所有权在后台完成写入前不得释放；失败、清空、停止和析构路径也必须恰好释放或转移一次。

### 2.3 失败边界

入队可能因容器分配失败而抛异常，任务提交也可能失败。实现前应明确：接收段的哪个时点视为成功、失败后段归谁所有，以及容器不应留下半条消息或破坏已有顺序。不得用“无字节复制”掩盖异常处理。

保持现有后台错误语义：写入或刷新失败后记录异常、停止该 Worker 的后续消费，按当前约定放弃剩余待写数据；后续调用及显式停止按现有约定报告。已经写出的前缀无法回滚，不能盲目重试造成重复。消息析构时的回调和异常处理也必须与现有行为一致，避免异常逃出析构函数。

按段写入可能改变失败发生的位置：同一批中前面的段可能已写入，而后面的段尚未写入。应测试并记录这一行为，不把整批输出说成原子操作。

## 3. 成本与预期

可确定的结构变化是，正常所有权交接不再把完整日志从消息缓冲区复制到 Worker 的连续生产者缓冲区，也不需要为了让生产者缓冲区增长而搬运已接收的日志。实际前台延迟和系统吞吐能否改善，仍取决于负载和实现。

需要同时关注以下成本：

- **段管理与内存：**每条日志各有缓冲区及管理信息，当前 `FlexibleBuffer` 默认初始大小为 1024 字节；短日志可能只使用其中一小部分。消费速度落后时，待处理段及其容量可能持续增长。当前方案不自动提供积压上限。
- **分配与复用：**接管存储后，每条新消息仍需取得自己的可写存储；移动对象、节点或指针的选择，以及是否复用已输出的缓冲区，可能影响分配次数和峰值内存。
- **输出次数：**一批 N 个段在现有 `LogFlush::write(const char *, size_t)` 接口下通常需调用 N 次，而当前连续批次通常调用一次。多次调用不一定对应多次系统调用：文件输出使用带缓冲的 `fwrite()`；但每段仍经过 `LogFile` 加锁，轮转文件还会检查日期和大小，标准 I/O 自身也有成本。
- **轮转与调用边界：**`LogFile::append()` 以每次调用的数据长度检查轮转；从整批一次追加改为逐段追加，文件边界可能随之变化。自定义 `LogFlush` 也可能观察到调用次数和每次传入的范围变化，需检查其兼容性；不得仅按最终字节序列判断所有行为一致。
- **性能取舍：**大消息可能更受益于省去字节复制；短消息、高条数时，额外段管理、调用和加锁可能抵消收益。不能先断言复制或多次写入一定是主要瓶颈。

第一版先按段输出并每批刷新一次。若测量显示输出调用成为瓶颈，再研究批量输出接口或平台的聚集写入；须分别处理平台支持、部分写入、错误、轮转和自定义输出目标的语义。将所有段重新拼成连续缓冲区虽可能减少调用，但会引入一次字节复制，是否值得应由测量决定。

### 3.1 小日志与聚集写入

多段字节可以构成一条逻辑上连续的输出流，而各段在内存中不必相邻。普通的 `write(data, len)` 或 `fwrite()` 每次接收一段连续内存；聚集写入接口则接收多组地址和长度，允许调用方将多段数据一次提交，而不用先在应用层复制到同一块连续内存。

以一批 100 条小日志为例，三种路径的差别是：

| 路径 | 消息进入 Worker 时 | 输出时 |
|---|---|---|
| 当前连续双缓冲 | 复制各条消息，合并到连续缓冲区 | 通常以一次 `LogFlush::write()` 提交整批 |
| 分段缓冲、逐段输出 | 转移各消息缓冲区的所有权，不复制消息字节 | 对每个非空段调用一次 `LogFlush::write()`，最后整批 `flush()` 一次 |
| 分段缓冲、聚集写入 | 同样转移所有权 | 将多个段的地址和长度作为一组提交，减少输出接口调用；具体次数受段数上限及部分写入影响 |

因此，聚集写入是分段方案的一个明确后续优化方向：同时避免提交时的额外字节复制，并有机会降低短日志、大批次场景下逐段输出的调用成本。它并不保证整体更快：需要准备和遍历段描述信息，每条消息的缓冲区分配和管理成本依然存在；短消息的连续复制也可能很便宜。实际效果需要比较前台延迟、整体吞吐和内存占用。

Linux 的 [`writev()`](https://man7.org/linux/man-pages/man2/writev.2.html) 按顺序写入一组 `iovec` 指向的内存；必须处理单次可提交段数的限制、部分写入和错误，并依据实际已写字节推进到正确的段与偏移。一次系统调用不代表所有段一定写完，也不代表内核内部没有复制或数据已经持久化。

Windows 的 [`WriteFileGather()`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefilegather) 同样能聚集多个内存段，但要求异步、无缓冲文件句柄，缓冲区需按内存页对齐，写入长度还受扇区对齐约束。当前每条日志的 `FlexibleBuffer` 并不保证满足这些条件，因此不能把它视为 `writev()` 的直接跨平台替代；如何在 Windows 上批量输出仍需单独研究。

当前文件输出经 `LogFile` 使用带缓冲的 `FILE*` 和 `fwrite()`。引入聚集写入需要重新设计与现有流缓冲的衔接，不能未经同步就把底层文件描述符写入与 `FILE*` 操作混用，否则可能破坏顺序；还要保留或明确调整文件轮转、输出目标扩展、锁、错误及刷新语义。输出完成前，各段及其描述信息须按相应同步或异步接口的要求保持有效。`flush()` 推动缓冲数据继续写出，本身不等同于持久化。

实施顺序保持简单：先完成分段所有权交接，使用逐段输出验证正确性并建立基线；再单独设计平台适配的批量输出，用同一负载与当前连续双缓冲、分段逐段输出比较。聚集写入的具体接口、跨平台实现和是否采用，均以正确性与测量结果为准。

### 3.2 Windows 后续研究：I/O Ring 批量提交

Windows 的 I/O Ring 是除逐段 `fwrite()` 和受对齐限制的 `WriteFileGather()` 之外，值得后续研究的一条路径。它可以为每个日志段构造独立的文件写入请求，再使用 [`SubmitIoRing()`](https://learn.microsoft.com/en-us/windows/win32/api/ioringapi/nf-ioringapi-submitioring) 批量提交已构造的请求；`IORING_BUFFER_REF` 支持引用普通地址或已注册的缓冲区。参见 [I/O Ring 接口](https://learn.microsoft.com/en-us/windows/win32/api/ioringapi/)、[缓冲区引用](https://learn.microsoft.com/en-us/windows/win32/api/ioringapi/ns-ioringapi-ioring_buffer_ref)以及 [BuildIoRingWriteFile 接口定义](https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/Storage/FileSystem/fn.BuildIoRingWriteFile.html)。

```text
已拥有的日志段 A、B、C
    → 分别构造写入请求，并指定各自的文件偏移
    → 批量提交请求
    → 分别检查完成结果，完成后释放对应的段
```

它可能允许后台在不先拼接日志字节的情况下，减少多次向内核提交请求的开销。但这**不是 `writev()` 式的单个聚集写入操作**：每个段仍是独立的写请求；批量提交不保证一次底层文件写入、完全无复制或性能优于现有方案。I/O Ring 的基础版本与写操作的支持版本不能混为一谈，须按实际系统检查写操作支持并准备回退路径。

后续研究和原型需要确认：

- **偏移与顺序：**明确如何从当前文件末尾为每个段分配互不重叠的偏移；不能假定异步请求按提交顺序完成。检查其他写入者、文件追加和轮转与偏移管理的关系。
- **短写与失败：**逐个检查完成结果；特别验证某一段失败或短写、后续段已经写入时的处理和错误报告，避免将有缺口的文件当作完整日志。提交失败和单个请求失败的语义不同，也需分别处理。
- **生命周期与关闭：**段和请求所需的数据保持有效直到相应操作完成；`flush()`、`stop()`、析构和轮转应等待或按明确约定处理在途请求，不能提前释放内存或文件句柄。
- **兼容与集成：**检查 Windows 版本、SDK、`IORING_OP_WRITE` 的运行时支持、文件句柄要求及不支持时的回退。现有输出使用 `FILE*` 和 `fwrite()`，不能忽略流缓冲状态而直接混用另一套文件写入路径；需重新明确输出顺序、锁、错误和刷新语义。
- **性能：**在真实 Windows 环境比较 I/O Ring、逐段 `fwrite()`、后台合并后写入，以及现有连续双缓冲；覆盖小日志、多段批次和不同批次大小。记录前台延迟、后台吞吐、请求及提交次数、内存、排空耗时和输出完整性。一次 `SubmitIoRing()` 处理多个请求不等同于只发生一次底层文件操作。

此项仅列为待办，尚未实现、运行或验证 I/O Ring 的写操作版本要求与实际性能；不因此改变分段缓冲第一版按段输出的计划。

## 4. 相关实现与参考

- [Folly IOBufQueue](https://github.com/facebook/folly/blob/main/folly/io/IOBufQueue.h)：可以接收并持有 IOBuf 链；其追加普通字节指针的接口仍复制。适合参考块的所有权交接和生命周期，不意味着 dlog 需要引入 Folly。
- [brpc IOBuf](https://github.com/apache/brpc/blob/master/docs/en/iobuf.md)：追加另一个 IOBuf 时不复制 payload，追加普通字符串时会复制。可参考可管理块之间的交接；其共享与引用管理比本方案需要的功能更广。
- [Boost.Beast multi_buffer](https://www.boost.org/latest/libs/beast/doc/html/beast/ref/boost__beast__basic_multi_buffer.html)：使用多个字节数组表示可增长缓冲区，适合参考分段遍历；它管理自己的存储，不应仅凭分段就认定可零拷贝接管现有 `FlexibleBuffer`。
- [Quill 的设计](https://github.com/odygrd/quill#-design)：前台将参数直接序列化到线程专用队列，后台再格式化。它避免采用先格式化整条消息再复制到队列的路径，但不是本方案的已格式化消息所有权转移。
- [muduo AsyncLogging](https://github.com/chenshuo/muduo/blob/master/muduo/base/AsyncLogging.cc)：日志行先复制到大缓冲区，再通过移动和交换交接大缓冲区；不能将大块交接无复制等同于日志行提交无复制。

这些资料用于理解设计取舍，不代表已经验证其在 dlog 中的性能。当前未确认与本方案完全相同的知名日志库实现。

## 5. 后续实施与验证

1. 明确段的拥有方式、回调的消费语义、公开接口兼容及失败时的所有权；设计被移动对象的不变量。
2. 实现最小的分段容器，并接入 `LogMessage`、`Logger` 和 Worker；保留裸指针追加的数据复制语义，按需要迁移调用方、公开头文件及测试。
3. 验证原消息和流销毁后，后台仍能取得完整数据；覆盖空消息、超长消息、内嵌零字节、连续多段、移动后状态和不发生交接字节复制。
4. 验证多生产者不交错、顺序、慢输出期间继续生产、任务退出竞态、正常停止排空，以及入队分配失败、任务提交失败、写入和 flush 失败；检查输出目标生命周期与异常传播。
5. 检查普通文件、轮转文件、终端和自定义 `LogFlush` 的行为，尤其是分段写入导致的轮转及回调边界变化；根据项目支持范围验证构建、安装产物和外部使用。
6. 与当前连续双缓冲方案在相同构建模式、消息内容和刷新策略下比较。参考 [性能测试计划](bench-plan.md)，覆盖短、中、长及混合消息、单/多生产者、低频、突发、持续和慢输出，包含计数输出与真实文件；重复运行并记录平台、构建配置及硬件。

性能比较至少记录前台提交吞吐和延迟分布、含后台排空的总吞吐与停止耗时、输出调用和批次大小、内存峰值及可获得的分配次数；同时校验记录数量、顺序和完整字节。分别观察前后台，避免把前台延迟改善误认为总体吞吐必然改善。先前线程池计划中的单次合成结果不能证明本方案的收益，也不能确定当前瓶颈。

完成标准：交接路径经验证不复制日志字节，现有顺序、生命周期、关闭与错误约定得到维护，接口及可观察行为变化已处理；性能和内存结果如实记录。即使基准未显示总体收益，也应先分析成本与目标负载，再决定是否采用或调整。
