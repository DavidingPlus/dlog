# 共享线程池接入计划

状态：独立线程池已实现，共享和日志接入仍在规划中。本文独立于现有 `docs/plan.md`，后续线程池工作在这里记录进度。

## 1. 目标与边界

让多个 `LogWorker` 共用一组后台线程，将现有的日志输出工作按批交给线程池执行，避免每创建一个 `Logger` 就长期占用一条后台线程。现有调用链仍为：

`Logger` → `LogWorker` 缓冲日志 → 线程池执行输出任务 → `LogFlush` 写入并刷新。

这次只调整现有日志链路的后台调度，不新增远程备份、多输出目标等功能，也不改变日志格式和现有调用方式。共享池默认使用 4 条线程；可在首次获取 `LogManager` 或使用默认日志宏之前通过 `LogManager::ConfigureThreadPool(threadCount)` 配置线程数。

需要保留的现有行为：

- `append()` 支持并发生产，完整记录按进入缓冲区的顺序保存；输出回调在后台执行，输出期间不持有生产者锁。
- 缓冲区写满后触发处理；未写满的数据按 `flushInterval` 定期处理，默认 3 秒，传入 0 时至少等待 1 秒。定时到期只是触发处理，实际输出时间受调度和 I/O 影响。
- 同一个 `LogWorker` 的输出按缓冲顺序串行执行；不同 Worker 可以并行执行，不承诺跨 Worker 的输出顺序。
- `start()`、`stop()` 和重复调用的现有语义保留：停止前由调用方停止生产；已启动的 Worker 在停止时处理剩余数据；未启动时调用 `stop()` 不消费缓存；停止后允许追加并再次启动。
- 后台输出失败时保存首个异常、停止该 Worker 的后续消费并丢弃剩余待写数据；后续非空 `append()`、`start()` 和显式 `stop()` 按现有约定报告异常，析构只负责回收。`Logger` 当前对提交和停止错误的处理方式不因本次改造改变。
- `LogWorker` 析构、`Logger::stop()` 和正常进程退出时，已接受的工作要按现有约定完成或报告失败；回调不能调用同一个 Worker 的停止或销毁操作这一约束保持不变。

共享线程池会改变调度特性：同一个 Worker 的不同批次不保证由同一条线程执行；多个 Worker 的输出任务可能竞争池线程，慢输出也可能延迟其他 Worker。不能承诺线程池一定提高吞吐量或降低延迟。

## 2. 核心设计

### 2.1 任务粒度

当前 `threadFunc()` 是长期运行的等待循环。不能直接把整个循环作为任务提交，否则每个 Worker 仍会长期占用池线程，Worker 数量超过池大小时，后续任务可能一直无法执行。

改为按需提交**有限的输出任务**：任务取得一批待处理缓冲区，按顺序执行输出，完成后释放池线程。同一个 Worker 同一时刻最多有一个输出任务处于排队或执行状态；任务结束前若又积累了待处理数据，按状态继续安排后续工作，避免重复提交或遗漏唤醒。

### 2.2 定时处理

使用一个共享的定时调度器跟踪已启动 Worker 的刷新时间，到期时通知对应 Worker 安排输出任务。定时等待由共享调度器承担，不让线程池工作线程或每个 Worker 各自长期等待。优先使用一条独立的定时线程；定时线程只负责调度，不执行用户输出回调。

定时触发、缓冲区写满和停止操作可能同时发生，必须通过 Worker 状态协调，避免重复任务、漏处理和顺序颠倒。定时触发时若没有数据，不调用输出回调；执行中有新日志到来时，下一批仍须得到处理。

### 2.3 共享对象与生命周期

由 `LogManager` 创建并持有共享线程池，后续多个 Worker 共用该实例；定时调度器的归属和具体接口在接入定时调度时确定，不预设必须新建运行时类。Worker 持有线程池的共享所有权，确保尚在使用时线程池不会因 Manager 释放引用而提前销毁。待执行任务必须保证其访问的 Worker 状态、缓冲区和输出目标有效，不能只捕获可能先销毁的裸指针。

独立创建与注册是两回事：普通 `Logger::BuildLogger()` 在内部从 Manager 获取共享线程池，无需注册；注册仍用于按名称查找，以及由 Manager 在关闭时主动停止已注册的 Logger。Manager 不知道未注册 Logger 的存在，未注册 Logger 仍需依靠调用方显式停止或自身正常析构来完成清理。

Manager 构造时会创建默认 Logger，不能让该 Logger 再通过 `GetInstance()` 获取尚在构造中的 Manager。实现时先初始化线程池，再通过内部创建接口将线程池传入默认 Logger；独立 Logger 则从已构造完成的 Manager 获取同一个实例。公开的 `LogWorker` 也可能被直接构造，须在接入前确定它如何获取或接收共享池，保留现有公开使用方式，不能只覆盖 Logger 路径。

停止 Worker 时，先取消其定时调度并处理与并发触发的竞态，再提交或等待最后一批工作；确认该 Worker 的定时回调和输出任务均不再访问其状态后，才能销毁状态及输出目标。运行时最后关闭定时器和线程池，并等待池内任务结束；关闭顺序不得形成循环等待或线程自连接。

共享所有权只保证对象不会因引用提前释放而销毁，不保证在任意线程释放最后一个引用都是安全的。要避免最后一个线程池引用在其工作线程执行任务时释放，导致析构时等待自身；同时避免线程池、任务和 Worker 之间形成无法释放的所有权环。Manager 析构后不能继续通过 `GetInstance()` 获取已经销毁的对象；程序关闭和 DLL 卸载期间何时停止独立 Logger、是否允许继续使用，必须结合实现明确约束并验证，不能仅靠 `shared_ptr` 作出保证。

“全局唯一”具体指**同一个 dlog 运行时实例内共享一个线程池**。跨 EXE/DLL 或多个独立静态链接副本是否能共享实例，不能仅凭函数内静态变量假定；实现时须结合当前 `LogManager` 所在模块及退出顺序确定所有权，并验证支持的场景。不得为通过退出测试而故意泄漏线程池或忽略任务。

### 2.4 失败与并发边界

- 不在持有 Worker 状态锁时运行输出回调或等待任务完成；明确定时器、线程池和 Worker 的锁顺序，避免锁反转。
- 任务提交失败、线程或定时器初始化失败时，不能让 Worker 误以为任务已经安排成功而永久等待；需回滚调度状态，并让错误按照对应入口的现有错误处理方式可见。
- 已进入队列的任务、正在执行的回调、定时触发和 `stop()` 并发时，均要能明确判断是否仍需安排后续任务。出现输出异常后不再继续消费该 Worker 的剩余数据。
- 调用方仍须在停止前结束生产；不额外承诺并发 `start()` / `stop()` 或从输出回调内停止自身。
- 当前待写缓冲区没有统一硬上限；本次不新增限流或丢弃策略。共享池积压可能增加内存占用，验证时应记录这一限制。

## 3. 分步实施

### 步骤 1：建立共享运行时

分三个小步建立共享资源；每步完成后先验证，再进入下一步。暂不把长期运行的 `threadFunc()` 塞进线程池，也不改变日志输出路径。

1. **共享线程池的归属（已实现，部分场景待验证）。** 由 Manager 持有共享线程池，默认 4 个线程，并通过 `getThreadPool()` 返回共享指针。首次获取 Manager 之前可以调用 `ConfigureThreadPool()` 设置线程数，该调用只保存配置，不创建 Manager；初始化前传入 0 会抛出异常，多次配置以最后一次成功调用为准。初始化后配置会向标准错误输出警告并忽略。当前访问方法是公开成员，面向日志组件使用；不假定跨 EXE/DLL 或多个静态链接副本必然唯一。构造或任务提交失败仍向调用方传播异常。
2. **Logger 创建路径。** 为默认 Logger 提供接收线程池的内部创建路径，避免 Manager 构造时递归调用 `GetInstance()`；独立创建的 Logger 从 Manager 获取同一线程池。明确直接创建 `LogWorker` 的路径和兼容性，避免仅为传递对象而提前更改现有输出行为。
3. **共享定时调度器。** 设计并实现统一的定时等待、注册和取消；明确它与 Manager、Worker 及线程池的所有权和关闭顺序。此时仍不改变现有 `threadFunc()` 的日志输出方式，实际 Worker 定时接入在步骤 3 完成。

**验证：**有限任务能够执行，多个任务可以共享工作线程；默认 Logger、独立 Logger 和直接使用 Worker 的路径符合各自设计；关闭时等待已接受任务完成；初始化和入队失败不会造成假成功或卡住。覆盖空队列和仍有任务时关闭、Manager 与独立 Logger 的不同销毁顺序，并分别记录 Windows DLL / 静态库和 Linux 的实际验证结果。

### 步骤 2：改造 `LogWorker` 的批次调度

保留现有缓冲和 `append()` 入口，将后台循环拆分成按需执行的批次输出任务；使用受锁保护的状态保证同一 Worker 最多一个任务排队或执行。完成一批后正确衔接处理中到来的新数据，不在输出期间持有生产者锁。

**验证：**单个 Worker 的多批数据完整且有序，跨缓冲区的二进制和长记录不丢失；多生产者写入时记录不交错；慢输出期间生产者仍可追加；多个 Worker 共享有限池线程时均能取得进展。

### 步骤 3：接入共享定时调度

为启动的 Worker 登记刷新时间，缓冲区写满时立即安排输出；未写满的数据在定时到期时安排输出。停止或销毁时撤销登记并处理与正在触发的定时事件之间的竞态。

**验证：**部分缓冲区无需停止即可在定时后输出；写满可提前触发；空缓冲区不调用输出；间隔为 0 时不会空转；定时与写满并发时不重复、不遗漏。测试应使用同步信号和合理超时，不把线程调度精确时间当作保证。

### 步骤 4：完善停止、异常和退出回收

实现停止时处理尾部数据并等待该 Worker 的任务退出；保持重复启动、停止和后台失败的现有行为。处理定时器注销、任务捕获的对象所有权、运行时关闭顺序以及初始化和入队失败。

**验证：**覆盖已启动和未启动时停止、停止后追加并重启、析构处理尾部、输出阻塞时停止等待、后台异常传播和失败后不继续输出；覆盖定时触发与停止竞态、多个 Worker 依次关闭及运行时最后回收。任何等待都应有测试超时，便于发现死锁。

### 步骤 5：集成验证与文档更新

通过 `Logger`、`LogManager` 和默认宏验证完整日志链路，保留已有 `LogWorker` 与 Logger 测试；根据实际实现更新 README、相关注释及本文状态。检查公开头文件、安装产物、静态库和动态库的影响。

**验证：**运行现有全量测试和新增并发测试；验证普通文件、滚动文件、终端输出及正常进程退出时的尾部日志。至少覆盖 Windows DLL / 静态库和 Linux 可用构建；EXE 使用 DLL 的退出路径继续回归。业务 DLL 内创建 Manager 的正常退出问题暂留 TODO，复现和研究方向见 [windows-dll-exit-todo.md](windows-dll-exit-todo.md)。未运行的环境必须如实记录。

### 步骤 6：比较与收尾

在相同构建模式和工作负载下，对比改造前后的线程数量、单个及多个 Logger 的吞吐量、输出延迟、峰值内存和停止耗时；包含慢输出目标。结果只用于判断当前实现的取舍，不作为先验性能承诺。

**完成标准：**现有对外功能和上述验证通过；共享池确实由多个 Worker 使用，同一 Worker 保持串行；进程退出与错误路径没有已知悬空访问或死锁。记录实测条件、结果和尚未验证的范围。
