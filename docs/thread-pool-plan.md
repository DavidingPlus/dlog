# 共享线程池接入计划

状态：共享线程池及 Logger 创建路径已完成；Worker 的输出尚未接入线程池。接下来先改调度策略，再改缓冲模型。本文独立于现有 `docs/plan.md`，后续线程池工作在这里记录进度。

## 1. 目标与边界

让多个 `LogWorker` 共用一组后台线程，将现有的日志输出工作按批交给线程池执行，避免每创建一个 `Logger` 就长期占用一条后台线程。现有调用链仍为：

`Logger` → `LogWorker` 缓冲日志 → 线程池执行输出任务 → `LogFlush` 写入并刷新。

这次先调整现有日志链路的后台调度，再单独改造缓冲模型；不新增远程备份、多输出目标等功能，也不改变日志格式。`LogWorker` 的构造参数和回调接口可能随改造变化，需要同步调用方、测试和文档。共享池默认使用 4 条线程；可在首次获取 `LogManager` 或使用默认日志宏之前通过 `LogManager::ConfigureThreadPool(threadCount)` 配置线程数。

需要保留的现有行为：

- `append()` 支持并发生产，完整记录按进入缓冲区的顺序保存；输出回调在后台执行，输出期间不持有生产者锁。
- 有非空数据就安排后台输出，不等待缓冲区写满或定时到期；实际输出时间受线程池调度和 I/O 影响，不承诺立即完成。
- 同一个 `LogWorker` 的输出按缓冲顺序串行执行；不同 Worker 可以并行执行，不承诺跨 Worker 的输出顺序。
- `start()`、`stop()` 和重复调用的现有语义保留：停止前由调用方停止生产；已启动的 Worker 在停止时处理剩余数据；未启动时调用 `stop()` 不消费缓存；停止后允许追加并再次启动。
- 后台输出失败时保存首个异常、停止该 Worker 的后续消费并丢弃剩余待写数据；后续非空 `append()`、`start()` 和显式 `stop()` 按现有约定报告异常，析构只负责回收。`Logger` 当前对提交和停止错误的处理方式不因本次改造改变。
- `LogWorker` 析构、`Logger::stop()` 和正常进程退出时，已接受的工作要按现有约定完成或报告失败；回调不能调用同一个 Worker 的停止或销毁操作这一约束保持不变。

共享线程池会改变调度特性：同一个 Worker 的不同批次不保证由同一条线程执行；多个 Worker 的输出任务可能竞争池线程，慢输出也可能延迟其他 Worker。不能承诺线程池一定提高吞吐量或降低延迟。

## 2. 核心设计

### 2.1 任务粒度

当前 `threadFunc()` 是长期运行的等待循环。不能直接把整个循环作为任务提交，否则每个 Worker 仍会长期占用池线程，Worker 数量超过池大小时，后续任务可能一直无法执行。

改为按需提交**有限的输出任务**：任务取得一批待处理缓冲区，按顺序执行输出，完成后释放池线程。同一个 Worker 同一时刻最多有一个输出任务处于排队或执行状态；任务结束前若又积累了待处理数据，按状态继续安排后续工作，避免重复提交或遗漏唤醒。

### 2.2 有数据就安排输出

`append()` 接受非空数据后，若当前 Worker 没有排队或执行中的输出任务，就向线程池提交有限任务；已有任务时只追加数据，由该任务继续衔接处理。当前生产者缓冲区未写满也须交给任务处理。没有日志时不提交任务，线程池工作线程在池自己的队列上等待。

任务完成一批后，在同一把状态锁下检查后续数据与任务状态，避免数据到来时漏掉调度；输出回调和等待均在锁外。无需共享定时调度器或 Worker 定时等待；`flushInterval` 不再有对应语义，实施时同步调整公开构造接口、调用方和测试。

### 2.3 共享对象与生命周期

由 `LogManager` 创建并持有共享线程池，后续多个 Worker 共用该实例。Worker 持有线程池的共享所有权，确保尚在使用时线程池不会因 Manager 释放引用而提前销毁。待执行任务必须保证其访问的 Worker 状态、缓冲区和输出目标有效，不能只捕获可能先销毁的裸指针。

`LogManager::buildLogger(name, ...)` 创建时自动注册并持有 Logger；调用方可通过名称查找，Manager 关闭时停止命名 Logger，并在析构时释放其持有的引用。默认 Logger 由 Manager 单独持有。

Manager 构造时会创建默认 Logger，不能让该 Logger 再通过 `GetInstance()` 获取尚在构造中的 Manager。实现时先初始化线程池，再通过内部创建接口将线程池传入默认 Logger；命名 Logger 也由该 Manager 创建并接收同一个实例。直接构造 `LogWorker` 时，由使用方自行负责提供和管理线程池；不为其另设自动获取 Manager 共享池的机制。

停止 Worker 时，处理剩余数据并等待排队或执行中的任务结束；确认任务不再访问其状态、缓冲区和输出目标后，才能销毁这些对象。关闭顺序不得形成循环等待或线程自连接。当前 `LogManager::shutdown()` 先停线程池再停 Logger，接入后 Worker 的尾部任务可能被拒绝；池中普通任务又可能写日志，不能简单颠倒顺序，先记录这一约束，在 Worker 任务调度和停止路径移植后，结合实际实现确定并验证最终关闭时序。

共享所有权只保证对象不会因引用提前释放而销毁，不保证在任意线程释放最后一个引用都是安全的。要避免最后一个线程池引用在其工作线程执行任务时释放，导致析构时等待自身；同时避免线程池、任务和 Worker 之间形成无法释放的所有权环。Manager 析构后不能继续通过 `GetInstance()` 获取已经销毁的对象；程序关闭和 DLL 卸载期间已创建的 Logger 何时停止、是否允许继续使用，必须结合实现明确约束并验证，不能仅靠 `shared_ptr` 作出保证。

“全局唯一”具体指**同一个 dlog 运行时实例内共享一个线程池**。跨 EXE/DLL 或多个独立静态链接副本是否能共享实例，不能仅凭函数内静态变量假定；实现时须结合当前 `LogManager` 所在模块及退出顺序确定所有权，并验证支持的场景。不得为通过退出测试而故意泄漏线程池或忽略任务。

### 2.4 失败与并发边界

- 不在持有 Worker 状态锁时运行输出回调或等待任务完成；明确线程池和 Worker 的锁顺序，避免锁反转。
- 任务提交失败或初始化失败时，不能让 Worker 误以为任务已经安排成功而永久等待；需回滚调度状态，并让错误按照对应入口的现有错误处理方式可见。
- 已进入队列的任务、正在执行的回调、追加数据和 `stop()` 衔接时，均要能明确判断是否仍需安排后续任务。出现输出异常后不再继续消费该 Worker 的剩余数据。
- 调用方仍须在停止前结束生产；不额外承诺并发 `start()` / `stop()` 或从输出回调内停止自身。
- 当前待写缓冲区没有统一硬上限；本次不新增限流或丢弃策略。共享池积压可能增加内存占用，验证时应记录这一限制。

## 3. 分步实施

先保持固定块缓冲，逐步移植调度、停止及错误处理，再结合实际实现调整并验证 Manager 的关闭时序；完整接入须同时满足这些路径，之后再单独改造缓冲模型。

### 已完成：共享线程池和 Logger 创建路径

`LogManager` 创建并持有共享池，默认 4 线程，可在初始化前配置。默认 Logger 由 Manager 内部创建，命名 Logger 由 `buildLogger(name, ...)` 创建并自动注册；线程池已传给 Worker，但 Worker 目前仍使用独立后台线程输出。Windows DLL 下已通过相关测试；其他平台和构建模式仍需按实际结果记录。

### 步骤 1：先移植 LogWorker 调度，保留现有缓冲

保留 `m_producerBuffer`、`m_pendingBuffers` 和固定块的记录拼接方式；将 `threadFunc()` 的长期等待循环改为线程池执行的有限批次任务。非空追加后安排输出，未满块也要被处理；同一 Worker 最多一个任务排队或执行，不同 Worker 可并行。任务结束前正确衔接新数据，输出时不持有生产者锁。

同步实现 Worker 级的停止等待、任务提交失败恢复和后台错误反馈，确保任务未结束时不会销毁其访问的对象。删除定时等待及 `flushInterval`；同步调整直接使用 Worker 的构造方式、调用方和测试。直接使用 Worker 时由调用方自行提供和管理线程池；线程池任务异常须由 Worker 显式保存和反馈，不能依赖未读取的 `future`。

**验证：**未满块和完整块均无需等待定时器即可安排输出；空数据不调用回调。覆盖同一 Worker 的顺序、长记录和二进制数据、多生产者不交错、慢输出时生产者可继续追加，以及多个 Worker 在有限线程中取得进展。覆盖数据到达与任务退出竞态、提交失败、后台异常、Worker 停止和析构；使用同步信号与合理超时。

### 步骤 2：结合移植结果调整 Manager 的关闭时序

Worker 调度和停止路径明确后，再依据实际任务生命周期调整 Manager 的关闭过程。重点处理池中的普通任务可能继续写日志，而 Worker 又需要池线程处理尾部数据的问题；不得简单交换当前两个停止调用。确认先后依赖和持有关系，避免循环等待、线程自连接或访问已销毁对象。

**验证：**覆盖线程池普通任务写日志、输出任务排队或执行、池线程繁忙、尾部未输出及 Worker 析构等场景；正常关闭排空已接受的数据，失败按既有约定反馈。以同步信号和超时检查等待关系，再认定调度接入完整。

### 步骤 3：调度阶段集成验证

通过默认日志宏、命名 Logger 和 Manager 验证完整链路；覆盖普通文件、轮转文件、终端及正常退出的尾部日志。确认多个 Worker 确实共享线程池，现有调用的顺序、错误反馈和停止语义符合设计；记录实际线程数量及构建环境。

**验证：**运行相关测试和全量测试，检查公开头文件、安装产物及外部使用；按可用环境覆盖 Windows DLL / 静态库和 Linux，并记录未验证范围。业务 DLL 内 Manager 的自动退出排空问题暂留 TODO，详见 [windows-dll-exit.md](windows-dll-exit.md)。

### 步骤 4：再改缓冲模型

在调度阶段通过验证后，单独重新设计 `m_producerBuffer` 和 `m_pendingBuffers`。优先比较可复用双缓冲与当前固定块队列，评估能否用项目已有的 `FlexibleBuffer` 简化实现；确定模型后再替换，而不是在调度改造中同时更换。同步处理 Worker 回调类型、超大记录、分配失败和公开调用方式。

**验证：**延续步骤 2、3 的顺序、完整性、并发、失败及关闭测试；增加输出变慢时的积压、内存增长和缓冲复用检查。在可用内存允许的范围内，新模型须处理超大日志，不照搬参考实现中可能无限等待或扩容不足的路径。

### 步骤 5：比较与收尾

在相同构建模式和工作负载下，对比改造前、调度改造后和缓冲改造后的线程数量、吞吐量、输出延迟、峰值内存和停止耗时，包含低流量和慢输出目标；记录实际结果，不预设性能提升。

**完成标准：**共享池用于实际输出，同一 Worker 输出有序，不同 Worker 可并行；停止、失败和退出路径通过验证；缓冲模型及对外接口、示例和文档一致，未验证的环境与限制有明确记录。
